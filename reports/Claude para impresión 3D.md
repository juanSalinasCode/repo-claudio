# Claude prepara, repara y lamina tu Ender

La mejor configuración para usar Claude Code como asistente de impresión 3D en noviembre de 2026 no pasa por ningún MCP de moda. Lo que mejor funciona es un **pipeline de scripts propios**: Claude escribe Python que analiza y repara la malla con **trimesh + manifold3d**, hace modificaciones de modelado con **`bpy` o `blender -b --python`**, lamina por CLI con un **perfil fijo de la Ender 3 V2 Neo** y deja la impresión física en manos humanas. Los MCP de Blender más populares, como ahujasid/blender-mcp (~35,5k estrellas) y el servidor oficial de Blender Lab, dependen de que Blender esté abierto con interfaz y un addon escuchando en un socket. No sirven tal cual en un contenedor sin pantalla. Los MCP de Blender que sí funcionan sin interfaz son proyectos de un solo autor y de madurez no verificada. Sobre el laminado, los motores tienen ventajas distintas. **PrusaSlicer** es el más cómodo por CLI siempre que se le pase un `.ini` aplanado. **OrcaSlicer** es el único que orienta y distribuye las piezas automáticamente desde la CLI. **CuraEngine** solo da resultados "como Cura" si alguien reconstruye la pila de perfiles, que es justo lo que hace el wrapper `print3d/cura_slice.py` de este repo. No hay ninguna skill pública hecha para Ender/Creality: casi todas apuntan a Bambu. Por eso conviene escribir una skill propia que fije el volumen real (**220×220×250 mm**), el start G-code con **G28 + G29** y unos perfiles PLA/PETG de partida para calibrar.

## Estado del entorno: todo lo necesario ya está instalado

El coordinador verificó el contenedor. Es Ubuntu 24.04 y tiene dos Blender. El primero es **Blender 4.0.2** de apt, que se usa como CLI con `blender -b`. El segundo es **Blender 5.3 como módulo Python `bpy`**, en el venv `/opt/3d/venv`, junto con **trimesh, manifold3d y numpy-stl**. También están instalados **PrusaSlicer 2.7.2** (apt) y **UltiMaker Cura 5.14.0**, este último como AppImage extraído en `/opt/3d/cura`. PrusaSlicer trae el perfil "Creality Ender-3 V2 Neo" dentro de `Creality.ini`, pero **su CLI 2.7 no puede seleccionar presets de sistema por nombre** y necesita un `.ini` aplanado. Cura incluye `creality_ender3v2neo.def.json` y los perfiles de calidad base de Creality. El repo contiene `print3d/cura_slice.py`, un wrapper en desarrollo que resuelve la pila de Cura (definición → variante → material → calidad → overrides del usuario) y le pasa los valores ya resueltos a CuraEngine. La red bloquea download.blender.org y docs.blender.org. Por eso las extensiones de Blender 4.2+ (como el Print3D Toolbox moderno) no se pueden descargar aquí, y la API de Blender hay que comprobarla con introspección (`get_rna_type()`) y no con la documentación.

Esto cambia algunas conclusiones de la investigación previa. Las notas suponían que Cura 5.13 o 5.14 sería la versión estable. Ahora se sabe que **5.14.0 está instalada y funciona como fuente de perfiles**. También daban por probable que PrusaSlicer incluyera el perfil de la V2 Neo, y está confirmado. Además, la investigación verificó que el Python del contenedor (3.13) es compatible con **`bpy` 5.3.0 de PyPI**, porque cada wheel de `bpy` exige una versión exacta de Python: 5.x usa 3.13 y 4.5 LTS usa 3.11 ([PyPI bpy](https://pypi.org/p/bpy); [pyvista-blender](https://kmarchais.github.io/pyvista-blender/getting-started/installation/)).

## Los MCP de Blender más populares necesitan una pantalla que este servidor no tiene

**ahujasid/blender-mcp** (renombrado a `mcp-for-blender`) es el estándar de facto, con **35,5k estrellas y 3,3k forks**. Funciona con un addon que abre un socket en `localhost:9876` y expone `execute_blender_code`, `get_scene_info` y otras herramientas. Su documentación no menciona ningún modo headless, y advierte que el socket **"has no authentication or encryption"** y que hay telemetría activa salvo que se defina `DISABLE_TELEMETRY=true` ([GitHub](https://github.com/ahujasid/blender-mcp)). El **servidor MCP oficial de Blender Lab**, para Blender 5.1+, también se distribuye como addon con socket en el mismo puerto. Según fuentes secundarias, la propia página de Blender Lab advierte que ejecuta el código generado por el LLM sin salvaguardas ([blender.org](https://www.blender.org/?p=96198); [comparativa strayspark](https://www.strayspark.studio/blog/official-blender-mcp-server-comparison-2026)). El problema queda resumido en otro proyecto: el puente a Blender de mcp-3D-printer-server "needs Blender open, because its add-on does not run in background mode" ([DMontgomery40](https://github.com/DMontgomery40/mcp-3D-printer-server)).

Para trabajar sin interfaz existen alternativas jóvenes. **@three-ws/blender-mcp** (nirholas) lanza `blender -b` en un proceso nuevo por cada llamada, convierte entre STL, GLB, OBJ, PLY, USD y otros formatos, devuelve previews renderizadas inline y se instala con `npx -y @three-ws/blender-mcp` ([GitHub](https://github.com/nirholas/blender-mcp)). **sandraschi/blender-mcp** lanza Blender como subproceso headless por defecto y expone 41 herramientas ([GitHub](https://github.com/sandraschi/blender-mcp)). **bpy-dev/blender-mcp** adapta el MCP de Blender Lab a "standalone bpy" ([GitHub](https://github.com/bpy-dev/blender-mcp)). **dcc-mcp-blender** ofrece un bootstrap `--background` pensado para CI ([GitHub](https://github.com/dcc-mcp/dcc-mcp-blender)). No encontré estrellas, fechas ni informes de alguien usándolos para editar STL destinados a impresión. La recomendación es no usar MCP para Blender: **Claude Code ya tiene Bash**, y un script `bpy` ejecutado con el venv o con `blender -b --factory-startup --python script.py -- args` es reproducible, se puede versionar y no abre puertos.

La investigación probó ese camino en este contenedor con Blender 4.0.2. A un cubo de 20 mm le restó un agujero de Ø6 (Boolean `EXACT`), le aplicó un chaflán de 1 mm (Bevel), fusionó vértices duplicados a 0,001 y recalculó las normales. El resultado tuvo **0 aristas no-manifold** y un volumen de **7302,55 mm³**, quedó apoyado en Z=0 y se exportó a STL. Hay dos detalles de versión que el agente tiene que conocer. En 4.0 existe `wm.stl_import`, pero **no `wm.stl_export`**, así que se exporta con `export_mesh.stl`. El exportador C++ `wm.stl_export` llegó en 4.1 ([release notes 4.1](https://developer.blender.org/docs/release_notes/4.1/pipeline_assets_io/)) y está disponible en el `bpy` 5.3 del venv. El segundo detalle es el **3D-Print Toolbox**. En 4.0 viene incluido (`object_print3d_utils`, 17 operadores `mesh.print3d_*`), pero su `thickness_min` por defecto es **0,001 unidades**, un valor absurdo si 1 unidad de Blender equivale a 1 mm. Además, desde 4.2 es una extensión aparte ([extensions.blender.org](https://extensions.blender.org/add-ons/print3d-toolbox)), y como download.blender.org está bloqueado no se puede instalar aquí. Por eso conviene que los chequeos críticos se calculen con bmesh o trimesh, que dan métricas estructuradas, en lugar de leer el informe del addon. STL no tiene unidades: con `global_scale=1` y `use_scene_unit=False`, **1 unidad de Blender = 1 mm** en el slicer ([manual 4.2 STL](https://docs.blender.org/manual/en/4.2/files/import_export/stl.html)).

## trimesh y manifold3d reparan, Blender modela y Tweaker-3 orienta

Para modificar STL que pasa el usuario (escalar, cortar, agujerear, unir piezas), el patrón que usan las skills publicadas es **trimesh + manifold3d** en Python sin interfaz. Es más fácil de verificar que Blender, y la skill m-esm/3d-print-modeling advierte que comprobar que la malla es watertight **"no basta"**: después de cada cambio hace falta una verificación visual, que ellos hacen con capturas headless de vistas iso, frontal, lateral, superior y cortes de sección ([m-esm](https://github.com/m-esm/3d-print-modeling)). Blender queda para el modelado más "artístico": solidify, bevel, texto en relieve convertido a malla o bisect para partir piezas que superan los 220 mm. **pymeshlab** (2025.7.post1 en PyPI) es el siguiente nivel para reparaciones serias, pero no está instalado y no encontré skills que lo usen. Para orientar las piezas, **Tweaker-3** busca por CLI la orientación que minimiza los soportes (`tweaker3 -i pieza.stl -x -min sur`) y existe también como plugin de Cura y de OctoPrint ([Tweaker-3](https://githubrp.bychv-a.workers.dev/ChristophSchranz/Tweaker-3); [Salzburg Research](https://www.salzburgresearch.at/?p=17279)). La otra opción es el `--orient` de OrcaSlicer.

El flujo recomendado tiene seis pasos, cada uno con verificación:

| Paso | Herramienta | Verificación |
|---|---|---|
| 1. Análisis | trimesh (`is_watertight`, `is_winding_consistent`, `bounds`, `volume`) | ¿Cabe en 220×220×245 mm? |
| 2. Reparación | trimesh `fix_normals`/`fill_holes`; manifold3d para booleanos | 0 aristas no-manifold |
| 3. Modificación | `bpy` 5.3 (venv) o `blender -b` 4.0 | Volumen y dimensiones esperados |
| 4. Orientación | Tweaker-3 u Orca `--orient` | Superficie de voladizos |
| 5. Colocación | Centrado en XY y apoyo en Z=0 | Render de vistas |
| 6. Laminado | CLI de slicer con perfil fijo | Revisión humana de la vista previa del G-code |

El bucle cerrado "script de Blender → revisión de malla → laminado → correcciones para el agente" ya existe como skill en **bsafh/print3d-orcaslicer**, aunque está hecho para una Orca Lab X2D ([GitHub](https://github.com/bsafh/print3d-orcaslicer)). **HighStormPVP/blender-3d-printing** aporta reglas de imprimibilidad y scripts de comprobación de manifold, pero funciona vía blender-mcp y no con `-b` ([GitHub](https://github.com/HighStormPVP/blender-3d-printing)). **tamer-afifi** insiste en medir con calibre e imprimir primero pruebas de ajuste ([GitHub](https://github.com/tamer-afifi/3d-print-design-skill)). Ninguna de las cerca de doce skills públicas pasa de una estrella ni está pensada para Creality. Sirven como plantillas, no para instalar sin revisar, porque ejecutan scripts.

## PrusaSlicer lamina sin fricción, Orca orienta y Cura exige reconstruir perfiles

| | PrusaSlicer (2.7.2 aquí) | OrcaSlicer | CuraEngine (Cura 5.14) |
|---|---|---|---|
| Perfil V2 Neo incluido | Sí (`Creality.ini`) | Sí, "Creality Ender-3 V2 Neo 0.4 nozzle" | Sí (`creality_ender3v2neo.def.json`) |
| Formato de perfil por CLI | `.ini` plano (`--load`) | JSON de máquina, proceso y filamento resueltos | `-j` definición + `-s` clave=valor |
| Salida | G-code directo (`--export-gcode`) | `plate_N.gcode` o `.gcode.3mf` | Solo G-code |
| Orientación automática | No por CLI (sin fuente) | `--orient`, `--arrange` | No |
| Fragilidad | Baja | Media (contexto GL, crashes reportados) | Alta sin wrapper |

**PrusaSlicer** es el motor recomendado. Su CLI corta sin pantalla con `--export-gcode`, `--load` repetible, `--center` y `--dont-arrange` ([manpage Ubuntu](https://manpages.ubuntu.com/manpages/jammy/man1/prusa-slicer.1.html)). Por ejemplo: `prusa-slicer -g --load config.ini --dont-arrange --center 125,105 model.stl` ([foro Prusa](https://forum.prusa3d.com/forum/prusaslicer/command-line-arrange)). La trampa es el perfil. Un "Export Config Bundle" **solo contiene los perfiles personalizados, no los de sistema** ([foro Prusa](https://forum.prusa3d.com/forum/prusaslicer/export-config-bundle-with-physical-printer-does-not-transfer-all-settings/?language=cs)), y mcp-3D-printer-server documenta que PrusaSlicer **ignora la configuración si se le pasa una carpeta** en lugar de un único config ([SLICING.md](https://github.com/DMontgomery40/mcp-3D-printer-server/blob/main/docs/SLICING.md)). A eso se suma lo que verificó el coordinador: la 2.7.2 no puede elegir el preset de sistema por nombre. La solución es aplanar una sola vez las secciones `printer`, `print` y `filament` de la V2 Neo en `Creality.ini`, siguiendo la cadena `inherits`, y guardar el resultado como `ender3v2neo_pla.ini` y `ender3v2neo_petg.ini`. Después basta con `--load` y overrides por flag, como `--layer-height 0.2` o `--fill-density 20%`. La rama master ya va por la **3.0.0-alpha14** con la CLI refactorizada ([version.inc](https://raw.githubusercontent.com/prusa3d/PrusaSlicer/master/version.inc)). Un `.ini` plano sobrevive a esa migración mejor que cualquier selección por nombre.

**OrcaSlicer** no está instalado. Tiene a favor la orientación y distribución automáticas por CLI (`--orient 1`, `--arrange 1`) y el perfil oficial de la V2 Neo ([Creality.json](https://raw.githubusercontent.com/SoftFever/OrcaSlicer/main/resources/profiles/Creality.json); [PrintConfig.cpp](https://raw.githubusercontent.com/SoftFever/OrcaSlicer/main/src/libslic3r/PrintConfig.cpp)). Pero no tiene `--export-gcode`: escribe `plate_1.gcode` en `--outputdir`. Además, aunque esté laminando, intenta crear un contexto OpenGL oculto para generar las miniaturas ([OrcaSlicer.cpp](https://raw.githubusercontent.com/SoftFever/OrcaSlicer/main/src/OrcaSlicer.cpp)), lo que en un servidor aconseja usar `xvfb-run`. Hay señales de que su CLI es frágil. La versión FULU OrcaSlicer-bambulab da **segfault en cada laminado**, y el MCP multislicer reordena las transformaciones "in Orca's order to avoid a CLI crash" ([SLICING.md](https://github.com/DMontgomery40/mcp-3D-printer-server/blob/main/docs/SLICING.md)). En el foro de Bambu se informa que la CLI de Bambu Studio, de la que deriva Orca, no aplicaba presets externos ([foro Bambu](https://forum.bambulab.com/t/cli-cannot-apply-external-presets/197842)). También hay un reporte de que el perfil de Orca para la V2 Neo **no espera a que la cama esté caliente antes de sondear** ([r/OrcaSlicer](https://pol1.lr.ggtyler.dev/r/OrcaSlicer/comments/1k1ikvv/auto_leveling_routine)).

**CuraEngine** tiene una CLI documentada (`CuraEngine slice -j def.json -s k=v -e0 ... -l model.stl -o out.gcode`), donde los ajustes se aplican al último objeto suministrado ([Application.cpp](https://raw.githubusercontent.com/Ultimaker/CuraEngine/main/src/Application.cpp)). El problema es que solo carga *definiciones*. Los perfiles de calidad, material e intent los aplica el frontend de Cura (Python/Uranium), así que sin ayuda se lamina con valores por defecto de `fdmprinter`. Eso es lo que resuelve `print3d/cura_slice.py`: recorre la pila definición → variante → material XML → calidad, evalúa las fórmulas y pasa todo resuelto. Tiene sentido si el usuario quiere el "comportamiento Cura" o abrir los resultados en Cura en su PC. Ojo con la posición: Creality tiene `machine_center_is_zero=false`, así que el STL hay que centrarlo antes (en 115,115 o 110,110) y apoyarlo en Z=0. Para pasar trabajo a Cura en el PC, conviene entregar **G-code más el STL ya orientado**. Los 3MF de proyecto de otros slicers se abren de forma parcial o con posiciones inconsistentes ([BambuStudio #3316](https://github.com/bambulab/BambuStudio/issues/3316); [comunidad UltiMaker](https://community.ultimaker.com/topic/38953-what-does-cura-do-with-3mf-files/)).

Sobre los MCP de slicer: **SpeakCAD Slicer** (directorio de plugins de Anthropic, v1.0.3, más de 380 impresoras) es lo más cómodo desde claude.ai, pero lamina en su web y el último paso es manual. **DMontgomery40/mcp-3D-printer-server** (270 estrellas, GPL-2.0) abstrae PrusaSlicer, Orca y CuraEngine mediante `SLICER_PATH` ([GitHub](https://github.com/DMontgomery40/mcp-3D-printer-server)). Ninguno de los dos añade nada que un script de 30 líneas con el `.ini` correcto no haga con más control. Tampoco existe un MCP de Cura dedicado.

## La Ender 3 V2 Neo necesita 220 mm, G29 y perfiles para calibrar

La máquina tiene **220×220×250 mm** de volumen, boquilla de 0,4 mm, extrusor Bowden, CR Touch (malla 4×4), cama magnética de PC sobre acero con un máximo de **100 °C** y velocidad máxima de **≤120 mm/s** ([Farnell](https://www.farnell.com/datasheets/3990939.pdf); [3DSourced](https://www.3dsourced.com/3d-printers/ender-3-neo-vs-v2-neo-max/)). La temperatura máxima de boquilla es dudosa: 260 °C según la hoja de datos y 250 °C según varias reseñas ([Clever Creations](https://clevercreations.org/creality-ender-3-v2-neo-review-specs/)). Conviene tratar 250 °C como techo, y con PETG mantenerse a 240 °C o menos. El perfil incluido en Cura tiene **dos defectos conocidos**. Declara la cama como 230×230, más grande que la real. Y su start G-code hace `G28` y una purga doble, pero **no incluye ni `G29` ni `M420`**, así que no usa el CR Touch ([def.json](https://github.com/Ultimaker/Cura/blob/main/resources/definitions/creality_ender3v2neo.def.json)). Con el firmware de serie, la comunidad indica que lo que funciona es **`G28` y luego `G29`** en cada impresión. `M420 S1` solo recarga una malla guardada y se reporta con fallos en el firmware 1.70 de Creality ([comunidad UltiMaker](https://community.ultimaker.com/topic/44724-i-feel-like-i-am-about-to-lose-my-mind-over-the-ender-3-v2/); [ídem](https://community.ultimaker.com/topic/33907-47-is-now-auto-bed-leveling-on-every-print/)). El start G-code recomendado calienta la cama y espera, deja la boquilla tibia a 150 °C para que no gotee, hace `G28`, luego `G29`, espera la temperatura de impresión y después ejecuta la purga original de Cura. El end G-code de `creality_base` es adecuado ([creality_base.def.json](https://github.com/Ultimaker/Cura/blob/main/resources/definitions/creality_base.def.json)).

Los valores de partida combinan el perfil de Cura (50 mm/s, primera capa a 20 mm/s, aceleración 500, jerk 8) con las guías para Bowden. Para la retracción, la recomendación es empezar en 5 mm y ajustar de a ±1 mm ([All3DP](https://all3dp.com/2/ender-3-retraction-settings-all-you-need-to-know/)). Para PLA se parte de 200 °C de boquilla y 60 °C de cama ([All3DP](https://all3dp.com/2/ender-3-cura-settings-best-ender-3-cura-profile/)). Para PETG, retracción de 4 mm a 25 mm/s y subir la velocidad de viaje si hay hilos ([All3DP PETG](https://all3dp.com/2/ender-3-petg-settings-profile/)). Creality sugiere en su blog 50–60 °C de cama para PETG ([Creality](https://www.creality.com/uk/blog/how-to-get-perfect-petg-prints-on-ender-3-correct-settings-first)), un valor bajo frente a lo que usa la comunidad.

| Parámetro | PLA | PETG |
|---|---|---|
| Boquilla | 200–210 °C (1ª capa +5) | 230–240 °C |
| Cama | 60 °C | 70–80 °C (pegamento de barra como desmoldeante sobre PC) |
| Retracción | 5 mm @ 45 mm/s (rango 4–6 @ 25–60) | 4–6 mm @ 25–40 mm/s |
| Velocidad | 50–60 mm/s, perímetro externo 25–30 | 40–50 mm/s |
| Primera capa | 0,24–0,28 mm @ 20 mm/s, ventilador 0 | Igual |
| Ventilador | 100 % desde la capa 2–3 | 30–50 % |
| Viaje / aceleración / jerk | 150 mm/s / 500 / 8 | 150 mm/s (Z-hop 0,2–0,4 opcional) / 500 / 8 |

Esta tabla es un punto de partida sintetizado, no un perfil validado en la máquina. Cada rollo pide una torre de temperatura y una de retracción. Las guías de calibración del firmware mriscoc (flujo, e-steps, PID, retracción) son la mejor referencia para la V2 Neo ([mriscoc](https://github.com/mriscoc/Ender3V2S1/wiki/Calibration-Guides)).

Hay un último eslabón opcional. La V2 Neo con su firmware de serie **no tiene red**, y todos los MCP de impresora (mcp-3D-printer-server, Kiln, printmcp) hablan con OctoPrint o Moonraker ([Kiln](https://pypi.org/project/kiln3d/)). Para controlarla desde Claude haría falta una Raspberry Pi con OctoPrint por USB. Incluso así, mcp-3D-printer-server advierte que un comando exitoso **no verifica que la impresión física haya salido bien**. Lo sensato es que Claude entregue el G-code y que una persona lo revise e imprima desde la microSD.

## Conclusión

La lección principal es que, en impresión 3D, **la integración más útil para Claude no es un MCP sino un contrato**: un perfil de máquina aplanado y versionado, más un conjunto de verificaciones numéricas (manifold, volumen, bounding box) que el agente debe pasar antes de laminar. Los MCP populares resuelven el problema de "Claude mueve Blender en mi escritorio", no el de "Claude produce G-code confiable en un servidor". En este contenedor, el único paso que sigue frágil es la resolución de perfiles: PrusaSlicer 2.7 no elige presets por nombre y CuraEngine no los aplica por sí solo. Por eso el trabajo de mayor rendimiento es terminar `cura_slice.py`, generar los `.ini` aplanados de PrusaSlicer y **corregir en ambos los dos defectos del perfil** (cama de 220 y `G29` en el start G-code).

El siguiente paso natural es empaquetar todo como una skill propia (`SKILL.md` con las especificaciones de la Ender, las recetas `bpy`/trimesh, los dos slicers y la tabla PLA/PETG) y validarla laminando la misma pieza con PrusaSlicer y con el wrapper de Cura, para comparar tiempos, consumo de filamento y vista previa. Quedan dudas abiertas que solo resuelve una impresión real: el Z-offset de cada unidad, si el firmware guarda la malla de forma fiable para usar `M420` y cuánto se desvían los perfiles sintetizados del óptimo de cada filamento.
